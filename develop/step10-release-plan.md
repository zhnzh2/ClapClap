# Step10 测试、迁移与分阶段上线方案

状态：上线前护栏建设中。

## 目标

Step10 不再新增核心玩法规则，重点是把 2.0 从“功能已跑通”推进到“可灰度、可回滚、可持续验证”。

本阶段坚持：

- 1.0 与 2.0 并列运行，任何 2.0 检查不能破坏 1.0 入口。
- 规则回放只读取存档事实，不重新随机、不重新推导历史结果。
- 迁移以只读校验先行，不直接批量改写生产数据。
- 记录信息尽量完整，页面默认保持简洁，详细信息通过折叠面板查看。

## 上线前检查

统一入口：

```powershell
.\scripts\check.ps1
```

检查内容：

- `python -m pytest`：运行全部 Python 测试，`pytest.ini` 会跳过 `tests/tmp*` 临时权限目录。
- `python scripts/validate_data.py --strict --summary`：只读检查现有 `data/` 目录的房间、对局和用户索引兼容性，并输出摘要。
- `python -m compileall -q app server scripts tests`：检查 Python 语法。
- `node --check server/static/js/**/*.js`：检查前端 JavaScript 语法。
- 模板内联 `<script>` 语法检查。

## 数据迁移策略

第一阶段只做校验，不自动改写：

```powershell
python scripts/validate_data.py --json
```

校验范围：

- `data/clapclap.db` 中的 `room_store`。
- `data/battles/*.json` 与 `data/battles/rub/*.json`。
- `data/users/User_*/battles` 用户对局索引。

兼容原则：

- 旧 1.0 对局缺少 `rule_version` 时仍按 1.0 读取。
- 2.0 对局建议包含 `schema_version: "2.0.0"`，但旧兼容记录只给 warning，不阻塞运行。
- 未知 `rule_version` 属于 error，上线前必须处理。
- 用户索引指向缺失对局属于 warning，可单独清理，不影响核心规则运行。

后续如果需要自动迁移，应另写显式脚本，先备份 `data/`，再逐条生成迁移报告，不能在服务启动时隐式改写历史记录。

## 分阶段上线

第一批：内部灰度

- 入口：保留 1.0 正式入口，2.0 通过 `/v2` 开放给测试用户。
- 功能：2.0 本地、多人房间、观战、匹配、回放和用户战绩。
- 要求：每次部署前运行 `scripts/check.ps1`。

第二批：公开 2.0 房间

- 开放 2.0 房间列表和观战入口。
- 保持 2.0 自动匹配为可关闭入口。
- 收集回放 JSON，优先修复回放缺字段和状态恢复问题。

第三批：公开 2.0 匹配

- 开启 `/v2/match`，按目标人数入队。
- 观察队列残留、重复提交、取消匹配和房间创建失败。
- 继续保留 1.0 `/match`，不共享队列。

第四批：产品化完善

- 补浏览器多会话自动化。
- 补压测、防刷和限流。
- 扩展多人战绩维度，例如淘汰关系、存活回合和不同人数表现。

## 回滚方案

- 入口级回滚：从大厅隐藏 2.0 入口，1.0 不受影响。
- 功能级回滚：关闭 `/v2/match`，保留邀请房间和本地模拟。
- 数据级回滚：不删除历史 2.0 JSON；回放按 `rule_version` 分流，未知版本显示明确错误。
- 代码级回滚：2.0 文件均位于 `app/v2/`、`server/routes/*v2*`、`server/static/js/pages/v2_*` 等独立路径，避免影响 1.0。

## 当前剩余风险

- 仍缺真正的多浏览器端到端自动化。当前 `check.ps1` 能检查页面脚本语法和后端协议测试，但不能替代真实浏览器并发点击。
- 多人战绩仍以冠军、名次和人数聚合为主，淘汰者/被淘汰者关系需要更稳定的事件字段后再统计。
- 生产数据迁移目前是只读校验方案，若未来要批量修复旧记录，需要单独写迁移器和备份流程。

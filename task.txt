================================================================================
 ClapClap / 拍拍 —— 2.0 多人化升级任务书
================================================================================

项目阶段：1.0 双人版已完整可用，当前进入 2.0 多人规则升级规划阶段。

当前状态一句话：现有系统已经是一个完整的双人联机网页游戏，但若要支持 2.0，
必须把"房间人数从 2 扩大"升级为"多人对局模型 + 2.0 规则状态机"的系统重构。

参考文档：
  - rules/version 1.0/rule.tex（1.0 双人版规则书）
  - rules/version 2.0/rule1.0.1.tex（2.0 多人版规则书）

================================================================================
一、这次升级的本质判断
================================================================================

【不是简单扩容】
  这次不能理解成"把房间人数上限从 2 改成 4、6 或更多"。
  当前系统从产品描述到程序结构都围绕双人设计：
    - 房间使用 p1/p2 座位，双方提交后立即统一结算
    - 自动匹配一次只配两人
    - 对局记录、回放、胜负关系和本地模式也都是双人模型
  当前 README 也把游戏、房间、匹配和本地模式明确描述为"双人对战"。

【2.0 引入的新复杂度】
  而 2.0 规则新增了：
    - 未操作对象与已操作对象
    - 攻击目标选择
    - 分段目标分配（黑洞→3、Shining→2 闪电、双吃→2 你吃）
    - 三连判定（三人循环克制 + 人数不对称时的选择规则）
    - 速度层结算（12 级速度，从闪到气/盾/加镐）
    - 同速目标声明与协商（意向公开 → 冲突识别 → 协商调整 → 确认）
    - 多人争抢同一目标（被攻击者选择攻击者）
    - 攻击后防御力归零
    - 玩家逐步淘汰
    - 最后一名存活者获胜

【本次升级的真实目标】
  保留现有账号、认证、聊天、部署和数据体系，
  重建多人对局模型与 2.0 回合结算流程。

  建议不要直接把现有 1.0 引擎改烂，而是让 1.0 双人模式和 2.0 多人模式暂时并存。
  旧记录继续按 1.0 回放，新房间可以选择规则版本，待 2.0 稳定后再决定是否弱化旧入口。

【基本可复用】
  ✅ 注册、登录、Session 认证
  ✅ 用户主页框架
  ✅ 管理员系统
  ✅ 用户验证和自动清理

  ✅ Socket.IO 基础连接
  ✅ 轮询兜底机制
  ✅ 全局弹窗系统（ModalUtils）

【需要扩展】
  - 用户对局索引（从双人胜负扩展到多人名次）
  - 聊天参与者身份（玩家 / 死亡玩家 / 观战者标识）

    - server/routes/match_routes.py —— 匹配 API

================================================================================
三、升级总路线
================================================================================

整个 2.0 升级按十个阶段推进：

  1. 冻结 2.0 数字版规则
  2. 建立规则版本体系
  3. 重构多人数据模型
  4. 独立完成 2.0 规则引擎
  5. 改造多人房间与生命周期
  6. 设计多人在线回合协议
  7. 改造前端房间页面
  8. 改造匹配、本地模式与观战
  9. 升级存档、回放与战绩
  10. 全量测试、迁移与分阶段上线

其中最重要的是前六步。房间页面不能先做，否则很容易围绕错误的结算模型反复返工。

当前优先顺序原则：
  - 先规则，后引擎，最后页面
  - 先邀请制多人房间，后公开房间，再自动匹配
  - 先让 2.0 在测试环境独立跑通，再接正式网页

================================================================================
四、阶段任务拆解
================================================================================

--------------------------------------------------------------------------------
【阶段 1：冻结 2.0 数字版规则】
--------------------------------------------------------------------------------

纸面规则允许玩家口头协商、临场判断和随机决定，但网页游戏必须把每一种情况变成
确定的程序流程。因此第一步不是写代码，而是补齐一份《2.0 数字版结算规范》。

1.1 明确房间基本参数

  需要确定：
    - 最少几名玩家才能开始
    - 房间人数上限
    - 房间人数是否固定，还是只设最大人数
    - 房主能否提前开始（人数未满时）
    - 是否允许中途加入
    - 开始后是否允许加入为观战者
    - 玩家死亡后是留在房间观战，还是退出房间
    - 是否存在固定座位顺序
    - 围成一圈是否只属于现实动作设定，还是会影响可攻击目标范围
    - 是否允许攻击任意存活玩家

  人数上限不应该散落在代码各处，后续需要形成统一配置；
  但具体数值必须先由规则和界面承载能力决定。

1.2 明确胜负边界

  2.0 规则规定最后一名存活者获胜，但程序还必须定义：
    - 同一回合所有人同时死亡如何处理
    - 最后两人同时死亡是否平局
    - 非法动作导致多人同时死亡时如何处理
    - 玩家掉线、超时、主动投降是否视为死亡
    - 房主离开是否转移房主
    - 对局中只剩一人在线但其他人未正式死亡时如何处理
    - 是否记录完整名次，还是只记录冠军与未获胜者
    - 同回合死亡的玩家是否并列

1.3 明确资源与死亡顺序

  目前规则中至少有几个必须在编码前定死的问题：
    - 1.0 中"镐"消耗 2 格气，2.0 的"加镐"段落没有写明消耗，必须确认最终规则
    - 玩家生命值降至 0 后，如果本回合稍后获得镐，是恢复生命还是已经失去获得资源的资格
    - 镐抵挡多段伤害时按每段处理还是按总伤害处理
    - 黑洞三段同时命中同一玩家时，镐在哪个时点消耗
    - 爆镐是在获得第二个镐的瞬间死亡，还是回合末统一判定
    - 被抢镐、获得镐、镐复活和爆镐之间的精确顺序
    - Fire、闪电的衍生资源是在攻击声明后获得、命中后获得，还是回合结算结束统一获得

1.4 把"协商"变成网页协议

  2.0 规则中最难数字化的部分不是攻击计算，而是同速协商。

  必须明确：
    - 同速玩家是否先秘密选择目标，再统一公开
    - 公开后可以修改几次
    - 是否必须所有相关玩家确认
    - 哪些玩家有权参与某一速度层的协商
    - 玩家长时间不确认时如何处理（超时默认行为）
    - 一般冲突中"没谈拢的人放空"如何由程序判断
    - 多人攻击同一目标时，被攻击者如何选择攻击者
    - 被攻击者不选择时如何随机
    - 随机结果如何记录，保证回放能够复现
    - 拆分黑洞、Shining、双吃时，所有分段目标如何一次性提交
    - 某一段找不到合法目标时，其他段是否仍然执行

  建议采用一套明确的在线流程：
    目标意向提交 → 同速意向公开 → 冲突识别 → 冲突处理 → 最终确认 → 同时结算
  而不是让玩家直接在聊天区协商后由某个人点击"结算"。

1.5 形成规则判例表

  至少要为以下情况逐一写出输入、处理过程和最终结果：
    - 普通单目标攻击
    - 同攻击力互相攻击
    - 攻击防御手势但未打穿
    - 攻击者防御归零
    - gi 无合法目标
    - gi 强制攻击
    - gi 攻击黑洞（反噬）
    - gi 抢镐
    - 你吃破
    - 你吃闪电
    - 双吃 Shining
    - 双吃拆分
    - Shining 拆分
    - 黑洞拆分
    - 一个三连（1,1,1）
    - 一多人数组成三连（1,1,多 / 1,多,多）
    - 两组三连（六人）
    - 多人攻击同一个目标
    - 同速强杀
    - 玩家在较快速度层成为已操作对象后，后续速度层对其的影响
    - 已操作玩家仍获得气、盾、火种、电池或镐
    - 同回合多人死亡
    - 全员死亡

  这一阶段的完成标准是：任何一个测试场景都能仅凭规范得到唯一结果。

交付物：
  - 《2.0 数字版结算规范》文档
  - 规则疑义清单（含逐条定稿结论）
  - 结算阶段流程图
  - 规则判例表（覆盖上述全部场景）
  - 多人胜负与超时规则

--------------------------------------------------------------------------------
【阶段 2：建立规则版本体系】
--------------------------------------------------------------------------------

目标：确保现有双人玩法、旧存档和线上稳定版本不被 2.0 直接破坏。

2.1 版本标识

  每个房间和每份对局记录都应明确保存：
    - 使用的规则版本（"1.0" / "2.0"）
    - 游戏模式（双人 / 多人 / 本地）
    - 房间人数配置
    - 初始资源配置
    - 参与者列表
    - 对局创建时使用的规则快照或规则版本号

2.2 引擎分发

  不建议简单把原有 GameEngine 改成同时塞满 1.0 与 2.0 的条件分支。更合理的是：
    - 1.0 结算逻辑保持稳定，不再大改
    - 2.0 建立独立结算实现（如 app/game_v2.py）
    - 房间服务根据规则版本调用对应引擎
    - 回放页面根据记录中的规则版本选择展示方式

2.3 兼容要求

    - 旧房间恢复时继续使用原来的规则
    - 旧 JSON 对局记录仍能正常读取
    - 旧回放页面不因新增多人字段报错
    - 新记录不能依赖后续可能变化的默认规则
    - 规则版本未知时应明确报错，不能猜测使用哪个版本

交付物：
  - 规则版本字段设计（数据库 + JSON + API）
  - 引擎分发机制
  - 旧数据兼容验证

--------------------------------------------------------------------------------
【阶段 3：重构多人数据模型】
--------------------------------------------------------------------------------

当前的双人模型在多个层面默认只有两名玩家。需要先把这些假设全部找出来，再逐层替换。

3.1 玩家模型（替代 PlayerState 中的双人假设）

  每位玩家除了现有资源状态，还需要具备：
    - 稳定的对局内身份（player_id / seat_index）
    - 座位或加入顺序
    - 存活、死亡、退出、掉线等状态
    - 本回合动作
    - 动作是否已经提交
    - 动作是否已经公开（亮招前为 false）
    - 当前是否为未操作对象
    - 当前是否为已操作对象
    - 当前目标意向（可能为多段）
    - 最终目标
    - 拆分动作的各段目标
    - 本速度层是否已确认
    - 死亡回合
    - 死亡原因（正常死亡 / 爆镐 / 爆气爆盾 / 蛤蟆蟆蛤 / 投降 / 超时）
    - 最终名次或并列组
    - 闪的剩余次数（每局最多 2 次）
    - 当前资源快照

  不能再通过 p1、p2 或"对方玩家"推导目标。

3.2 对局模型（替代 GameState 中的 p1/p2）

  多人对局应保存：
    - 所有参与者（list[PlayerState]）
    - 所有仍存活的玩家
    - 已淘汰玩家（含淘汰顺序）
    - 当前回合数
    - 当前阶段（waiting_moves / flashing / three_chain / speed_layer / finished）
    - 当前速度层
    - 当前速度层涉及的玩家
    - 当前目标声明集合
    - 当前冲突集合
    - 当前待决策玩家
    - 当前三连结构
    - 当前随机裁定结果
    - 当前结算事件序列
    - 游戏是否结束
    - 获胜者或平局结果

3.3 房间模型（替代 Room 中的 p1/p2）

  房间需要从"两个座位"转成：
    - 参战席位集合（list[Seat]）
    - 观战者集合
    - 房主
    - 人数上限
    - 最少开始人数
    - 开始条件（全员准备 / 房主手动 / 满员自动）
    - 每位玩家准备状态
    - 规则版本
    - 是否已开始
    - 是否允许中途观战
    - 断线保留宽限期
    - 重赛投票状态

3.4 回合模型（替代 RoundLog 中的 p1_move/p2_move）

  不能只保存"玩家 A 动作、玩家 B 动作、结果"。需要保存：
    - 所有人提交的原始动作
    - 资源合法性检查结果
    - 亮招结果
    - 三连判定结果
    - 每个速度层的输入
    - 初始目标意向
    - 冲突与调整过程
    - 最终目标
    - 每次有效交互
    - 已操作状态变化序列
    - 防御力归零事件
    - 伤害事件序列
    - 资源获得与消耗事件
    - 死亡和淘汰事件
    - 回合结束快照（每位玩家回合前后资源）

交付物：
  - 多人 Player / Game / Room / Round 数据模型定义
  - 与现有 1.0 模型的对照表
  - 序列化/反序列化方案

--------------------------------------------------------------------------------
【阶段 4：独立实现 2.0 规则引擎】
--------------------------------------------------------------------------------

这是整个项目的核心。目标：让 2.0 引擎脱离网页独立运行。

4.1 将结算拆成明确阶段

  阶段 A：动作提交与冻结
    所有存活玩家分别提交一个动作。
    全部提交前：
      - 其他玩家看不到具体动作
      - 已提交玩家可以看到自己已提交
      - 是否允许修改动作必须由规则确定
      - 服务器验证提交者身份
      - 服务器不提前执行结算
    全部提交后冻结动作。

  阶段 B：资源合法性检查
    检查：
      - 动作是否存在
      - 资源是否足够（气/盾消耗）
      - 是否超过闪的次数（每局 2 次）
      - 分段数量是否正确（黑洞 3/Shining 2/双吃 2）
      - 是否提交了不合规参数
    爆气、爆盾、非法动作等处罚在这里形成明确事件。

  阶段 C：统一亮招
    把所有玩家本回合动作同时公开。
    此时不能直接结算普通攻击，而是进入多人规则流程。

  阶段 D：闪结算
      - 使用闪的玩家立即成为已操作对象
      - 本回合不能再成为任何攻击或锦囊目标
      - 从后续目标集合中排除

  阶段 E：三连检测
    规则引擎根据当前动作关系：
      - 寻找可能的三连结构（gi—你吃/双吃—破 或 gi—黑洞—其他攻击）
      - 判断是否需要玩家选择三连人选（当出现 1,1,多 或 1,多,多 时）
      - 判断是否存在两组独立三连（六人，直接结束回合）
      - 处理三连中的 Fire（仍获得火种）、闪电（不获得电池）等资源结果
      - 将三连参与者标记为已操作对象

    三连人选不能由服务器随意选择。规则规定由特定玩家选择时，
    必须进入等待该玩家决策的状态。

  阶段 F：速度层循环
    按 2.0 规则规定的顺序逐层处理：
      1. 你吃、双吃
      2. 攻击黑洞的 gi
      3. 黑洞
      4. 如来、Shining
      5. 冷锋、烈焰
      6. 造成伤害或抢镐的 gi
      7. 破、闪电
      8. Fire
      9. 无目标 gi
      10. 气、盾、加镐

    闪和三连已经在之前处理。

    每一层都需要：
      - 找出仍有资格操作的玩家（未操作对象 + 该速度层的手势）
      - 计算每个玩家的合法目标（由后端规则引擎计算）
      - 接收目标意向
      - 检测同速冲突（一般冲突 / 多攻击少）
      - 等待必要的玩家决策
      - 确定最终方案
      - 同时执行该速度层（攻击、防御归零、伤害）
      - 更新已操作状态
      - 生成结算事件

  阶段 G：资源和伤害收尾
    处理：
      - 气和盾增加
      - Fire 获得火种
      - 闪电获得电池（被吃掉的除外）
      - 加镐（被抢镐的除外）
      - 镐抵挡伤害
      - 爆镐判定
      - 生命值变化

  阶段 H：死亡与胜负
      - 统一标记本回合死亡玩家
      - 从下一回合参战列表中移除
      - 计算是否只剩一人
      - 计算是否全员死亡
      - 记录淘汰顺序和原因
      - 决定进入下一回合还是结束游戏

4.2 引擎必须是可暂停、可恢复的状态机

  1.0 可以在双方提交后直接返回结果；2.0 经常需要等待玩家补充决策。

  因此 2.0 引擎应当是一个可以暂停和继续的状态机：
    - 当前可以继续自动结算时，服务器继续执行
    - 需要玩家选择目标时，暂停并广播待办（谁需要选择、合法目标有哪些）
    - 玩家提交决策后，从准确位置恢复
    - 需要冲突处理时，再次暂停
    - 所有条件满足后继续结算

  这是本次架构变化中最关键的一点。

4.3 所有随机裁定必须可复现

  如果协商失败需要随机决定：
    - 随机裁定必须由服务器执行
    - 结果必须写入对局记录
    - 最好保存本次随机裁定使用的依据（如使用对局 ID + 回合数作为种子）
    - 回放页面直接读取结果，不能重新随机

交付物：
  - 多人状态模型（Player / Game / Room / Round）
  - 规则状态机（含暂停/恢复机制）
  - 命令行或测试代码驱动完整对局
  - 完整单元测试（覆盖阶段 1 中所有判例）

【阶段 5：多人房间改造】
--------------------------------------------------------------------------------

目标：从双人房间生命周期升级到多人房间生命周期。

5.1 创建房间

  创建页面需要增加：
    - 规则版本（1.0 / 2.0）
    - 人数上限
    - 是否公开
    - 是否允许观战
    - 是否需要密码
    - 开始方式（满员自动 / 房主手动 / 全员准备）
    - 可能存在的初始生命或自定义设置

  首个版本不建议同时开放大量自定义规则，先完成标准 2.0 房间。

5.2 加入房间

  加入流程要区分：
    - 加入参战席位
    - 加入观战席位
    - 房间已满
    - 对局已经开始
    - 原玩家断线重连
    - 已淘汰玩家恢复连接
    - 同一账号重复进入

  player_token 不再对应 p1/p2，而应与具体参与者身份绑定。

5.3 房间大厅（开局前）

  显示：
    - 玩家名单
    - 房主标识
    - 当前人数与人数上限
    - 准备状态
    - 规则版本
    - 观战人数
    - 房间设置摘要
    - 开始按钮（仅房主可见/可操作）

5.4 开始机制

  需要从"双人到齐即可开始"改成明确的多人开始协议：
    - 房主发起开始
    - 是否要求所有人准备
    - 人数不足时禁止开始
    - 开始后锁定参战名单
    - 未准备玩家如何处理（强制准备 / 移出参战席 / 转为观战）

5.5 退出和掉线

  需要区分：
    - 开局前主动退出
    - 开局后主动投降
    - 短暂断线（保留宽限期）
    - 长时间离线（自动判定）
    - 页面刷新（重连恢复）
    - 服务重启后恢复
    - 已死亡玩家退出观战

  现有的房间恢复、轮询兜底和 Socket.IO 实时同步可以继续使用，
  但状态恢复内容要扩展到多人阶段和待决策事项。

5.6 重赛机制

  原来的"双确认 reset"需要改为多人方案：
    - 房主发起重赛投票
    - 所有仍在房间的原参战玩家分别表态
    - 明确需要全票还是达到某个条件（如半数以上）
    - 不参加重赛者转为观战或离开
    - 重新确定参战名单和座位

  该规则必须先确定，不能直接沿用双人双确认。

交付物：
  - 多人房间创建/加入/离开 API
  - 房间大厅状态管理
  - 多人开始协议
  - 重赛投票机制
  - 断线/重连状态恢复

【阶段 6：多人在线回合协议】
--------------------------------------------------------------------------------

多人版页面不能只保留"选择动作—提交—看结果"三个步骤。

6.1 等待出招

  每位存活玩家：
    - 选择一个动作
    - 看到自己的资源
    - 看到哪些动作当前资源允许使用（由后端返回合法动作列表）
    - 提交动作
    - 等待其他玩家
  页面只能显示"某玩家已提交"，不能提前显示其动作。

6.2 全员亮招

  所有玩家提交后：
    - 同时显示全部动作
    - 标识非法动作或资源不足（爆气/爆盾/蚂蚁）
    - 显示闪和三连检测结果
    - 显示即将进入的速度层

6.3 等待目标选择

  轮到某速度层时，相关玩家看到：
    - 自己当前手势
    - 所有合法目标（由后端计算并返回）
    - 不合法目标及原因
    - 放空选项（gi 除外）
    - 拆分动作的多个目标槽（黑洞 3 个、Shining 2 个、双吃 2 个）
    - 当前提交状态

  目标合法性必须由后端计算。前端可以禁用按钮，但不能自己决定规则。

6.4 同速意向公开

  所有相关玩家提交后：
    - 统一公开目标意向
    - 显示冲突关系
    - 标出谁需要重新选择
    - 标出谁拥有决定权（多攻击少时被攻击者）
    - 显示确认状态

6.5 冲突处理

  可能出现不同的交互：
    - 玩家修改自己的目标
    - 被多人攻击者选择其中一名攻击者
    - 三连指定玩家选择参与者
    - 拆分动作重新分配各段目标
    - 超时后执行规则规定的默认处理

6.6 速度层结算展示

  每个速度层完成后显示：
    - 谁攻击了谁
    - 哪些攻击对掉
    - 哪些攻击放空
    - 哪些锦囊生效
    - 哪些玩家成为已操作对象
    - 哪些玩家防御力归零
    - 造成多少伤害
    - 资源如何变化

  然后自动进入下一速度层，或等待用户点击继续观看。

6.7 回合总结

  显示：
    - 每位玩家回合前后资源
    - 生命值变化
    - 镐变化
    - 死亡玩家及原因
    - 当前存活人数
    - 下一回合状态
    - 对局是否结束

交付物：
  - 完整的回合状态机协议定义（前后端接口）
  - 每个阶段的前后端数据格式
  - 超时和默认行为规则

【阶段 7：前端页面改造】
--------------------------------------------------------------------------------

7.1 职责拆分

  当前房间详情页和脚本已经偏大，这次不适合继续把多人逻辑堆进同一个文件。
  现有路线图也已经把房间模板和脚本过大列为高优先级问题。

  建议至少按功能拆分为：
    - 房间大厅
    - 玩家列表
    - 自己的操作区
    - 动作选择区
    - 目标选择区
    - 协商与冲突区
    - 速度层进度
    - 结算事件展示
    - 聊天区
    - 断线与恢复处理

  这里说的是职责拆分，不应在没有读取现有源码的情况下直接确定新的文件名。

7.2 玩家展示

  双人左右布局要改成可扩展布局。每个玩家卡片至少展示：
    - 用户名
    - 座位或顺序
    - 存活状态
    - 生命值
    - 各类资源
    - 本回合是否已提交
    - 亮招后的动作
    - 未操作或已操作状态
    - 当前目标
    - 是否掉线
    - 是否房主

  桌面端可以使用环形、网格或横向列表；移动端必须能折叠，
  否则多人状态会挤满屏幕。

7.3 私密信息保护

  必须防止：
    - 在 Socket.IO 广播中提前发送其他玩家动作
    - 在轮询接口中提前返回隐藏动作
    - 在页面 HTML 或 JavaScript 状态中包含尚未公开的动作
    - 观战者提前看到动作
    - 重连玩家从历史状态中读到未公开信息

  不能只依靠前端"隐藏元素"。后端必须在广播前过滤私密字段。

7.4 聊天系统

  聊天基础可以保留，但要补充：
    - 玩家、死亡玩家和观战者身份标识
    - 是否允许淘汰玩家发言
    - 是否允许观战者发言
    - 对局协商是否通过独立交互完成，而不是依赖聊天
    - 系统结算消息与普通聊天消息的视觉区分

交付物：
  - 拆分后的前端文件结构
  - 多人玩家面板
  - 目标选择界面
  - 结算时间线组件
  - 观战视图
  - 移动端基本适配

【阶段 8：匹配、本地模式与观战】
--------------------------------------------------------------------------------

8.1 自动匹配

  当前匹配系统是单等待槽，只适合一人等待另一人的双人模式，
  这一点已经列入现有已知问题。

  多人匹配需要重新设计：
    - 按规则版本分队列
    - 按目标人数分队列
    - 已匹配人数显示
    - 是否允许部分人先进入房间等待
    - 有人取消后的回退
    - 有人掉线后的补位
    - 匹配成功后的确认阶段
    - 超时后继续等待还是降低人数要求

  上线顺序：
    1. 先做邀请制多人房间
    2. 再做公开房间
    3. 最后做多人自动匹配

  不要先改匹配系统，因为规则和房间都未稳定时，多人匹配很难测试。

8.2 本地模式

  当前本地模式是同屏双人。多人本地模式会遇到动作保密问题。

  可以分两种方向：
    - 裁判模式：所有玩家现实中同时出手，网页只负责输入结果和辅助结算
    - 传递设备模式：玩家依次秘密选择动作，设备在每人之间遮挡，但节奏较慢

  更符合原始拍拍玩法的是裁判模式。网页承担：
    - 录入所有人动作
    - 提示三连
    - 处理速度层
    - 提示合法目标
    - 记录伤害和资源

  多人本地模式可放在在线多人基本跑通之后开发。

8.3 观战模式

  多人化后观战价值会明显提高，需要处理：
    - 观战者加入与退出
    - 是否能看到未公开动作（不能）
    - 是否能参与聊天
    - 是否能看到玩家目标选择过程
    - 服务重启后的观战恢复
    - 已死亡玩家是否自动转为观战

交付物：
  - 邀请制多人房间
  - 公开房间列表
  - 裁判模式本地多人
  - 观战功能
  - 多人匹配队列（最后一批）

【阶段 9：记录、回放与战绩升级】
--------------------------------------------------------------------------------

9.1 对局记录

  当前记录以完整 JSON 保存参与者、回合、聊天和胜负，基础可以保留。
  但多人记录需要扩展为事件化结构。

  每个回合至少应能重现：
    - 所有人的动作
    - 资源检查结果
    - 三连选择过程
    - 每个速度层的输入与输出
    - 每次目标声明
    - 冲突决定
    - 随机裁定（含种子/依据）
    - 分段目标
    - 伤害事件
    - 资源变化
    - 淘汰事件
    - 最终排名

9.2 回放页面

  多人回放不能只显示一行双方动作。建议支持：
    - 回合总览
    - 玩家资源表
    - 速度层时间线
    - 目标关系图或文字列表
    - 三连高亮
    - 淘汰事件
    - 最终名次
    - 聊天记录

  回放页面根据记录中的规则版本选择展示方式（1.0 用旧回放，2.0 用新回放）。

9.3 用户战绩

  双人战绩中的"胜/负"需要扩展为：
    - 冠军次数
    - 参赛次数
    - 最终名次
    - 平均名次
    - 存活回合数
    - 淘汰方式
    - 被谁淘汰
    - 自己淘汰了谁
    - 不同人数房间的表现
    - 1.0 与 2.0 分开统计

  旧记录缺少名次时不能自行推测，应按旧版双人数据展示（胜/负）。

9.4 注销与对局关联

  现有系统会在用户注销时标记关联对局，并在全员注销后移入 rub/。
  多人对局需要把"全员注销"的判断从两名参与者扩展到完整参与者集合。
  现有用户索引和注销清理机制可以继续复用。

交付物：
  - 多人 JSON 存档格式
  - 多人回放页面
  - 多人战绩统计
  - 注销关联更新

【阶段 10：测试、迁移与上线】
--------------------------------------------------------------------------------

10.1 纯规则测试

  覆盖：
    - 3 人、4 人以及人数上限下的基本结算
    - 每种手势的合法与非法资源
    - 每个速度层的结算正确性
    - 已操作状态变化
    - 所有三连结构（1,1,1 / 1,1,多 / 1,多,多 / 两组三连）
    - 分段技能（黑洞/Shining/双吃拆分）
    - 同速冲突（一般冲突 / 多攻击少）
    - 防御归零
    - 放空
    - 镐与死亡（爆镐/抢镐/镐复活/镐挡多段伤害）
    - 同时死亡
    - 胜负判定（最后存活/全员死亡/平局）

10.2 状态机测试

  重点测试暂停和恢复：
    - 等待全部出招
    - 等待三连人选
    - 等待目标选择
    - 等待冲突处理
    - 玩家重复提交
    - 非相关玩家提交决策（应被拒绝）
    - 过期决策
    - 断线后恢复
    - 服务重启后恢复

10.3 房间测试

    - 多人依次加入
    - 房间满员拒绝
    - 房主转移
    - 开始条件验证
    - 观战加入
    - 玩家中途退出
    - 淘汰后观战
    - 重赛投票
    - 清理过期房间

10.4 网络测试

    - Socket.IO 广播是否只发给正确房间
    - 私密动作是否泄露
    - 多人同时提交
    - 多人同时修改目标
    - 同一请求重复发送
    - 网络延迟导致的乱序
    - 轮询与 Socket.IO 同时到达
    - 多进程部署下的一致性

10.5 回放一致性测试

  对任意对局：
    重新读取初始状态和完整事件记录，应得到与最终存档相同的状态。

10.6 浏览器端自动化

  现有项目缺少浏览器端交互自动化，这在多人版会变成明显风险。
  至少应覆盖多个浏览器会话：
    - 多人加入同一房间
    - 同时出招
    - 目标选择
    - 冲突处理
    - 淘汰
    - 重连
    - 对局结束
    - 回放打开

10.7 上线节奏

  第一批：内部规则验证
    只开放：
      - 2.0 测试房间
      - 邀请加入
      - 固定标准规则
      - 不接入自动匹配
      - 保留 1.0 正式入口
    目标：验证规则引擎和多人状态机

  第二批：多人房间公开测试
    增加：
      - 房间列表
      - 公开房间
      - 观战
      - 基础重赛
      - 完整存档与回放

  第三批：多人自动匹配
    规则和房间稳定后，再上线：
      - 按人数匹配
      - 匹配确认
      - 取消与掉线恢复
      - 队列状态展示

  第四批：产品化完善
    最后补充：
      - 手机端多人布局
      - 聚合战绩
      - 房主高级设置
      - 更完整的异常提示
      - 并发压测
      - 防刷与限流
      - AI 多人玩家

  上线时必须为数据库和 JSON 记录增加显式版本迁移机制。
  当前项目尚无自动数据迁移，这已经是现有已知问题之一。

交付物：
  - 分层测试用例
  - 浏览器自动化脚本
  - 数据迁移方案
  - 灰度发布计划

六、核心风险与开发原则
================================================================================

【核心风险】
  1. 把多人功能继续堆在双人字段上，导致后续无法维护
  2. 让前端自己决定规则（合法目标、速度顺序、冲突裁决），导致客户端与服务端不一致
  3. 先做页面再补规则，反复返工
  4. 把 1.0 与 2.0 混在一个函数里，兼容性快速失控
  5. 忽略存档版本和随机裁定记录，导致回放不可复现
  6. 多人状态下私密动作泄露（广播未过滤、重连返回未公开数据）
  7. 状态机暂停时无超时机制，一个玩家卡住整个对局

【本轮升级原则】
  1. 规则正确性 > 页面速度 > 视觉打磨
  2. 以后端规则引擎为准，前端只负责显示与提交
  3. 1.0 保持稳定，2.0 独立演进
  4. 先建立参与者集合和状态机，再谈 UI
  5. 所有暂停、恢复、随机和冲突都必须能被记录和回放
  6. 不要在原有双人字段上不断追加多人特例——从参与者集合重新建模
  7. 不要让前端决定规则——合法目标、速度顺序、冲突和伤害全部以后端为准
  8. 不要先做界面再补规则——必须先让 2.0 引擎在测试环境中完整跑完多人对局

二、项目技术架构总览
================================================================================

前端层（Jinja2 模板 + 原生 JS）
  - 模板引擎渲染页面结构
  - 原生 HTML/CSS/JS，无框架依赖
  - Socket.IO 客户端做实时通信
  - localStorage/sessionStorage 做身份与房间恢复缓存

服务层（Flask + Flask-SocketIO）
  - HTTP 路由：页面渲染 + RESTful API
  - WebSocket 事件：房间状态实时推送
  - 业务逻辑层（services/）隔离路由与核心引擎

核心引擎层（app/）
  - 纯 Python 规则结算，无外部依赖
  - GameEngine 单次调用完成回合结算
  - 状态序列化用于持久化和网络传输
  - 房间管理器管理房间生命周期
  - 匹配队列管理匹配状态

持久化层
  - SQLite（storage.py）
  - 房间状态持久化
  - 匹配状态持久化

三、当前已知问题和观察
================================================================================

【优先级：高】

1. 前端模板文件偏大
   - local.html、room_detail.html 将 HTML/CSS/JS 集中在单文件
   - 导致：难维护、难定位 bug、难复用组件、改动容易互相影响

2. 房间页 UI 仍在持续打磨中
   - 历史记录展示、当前对局状态区仍需优化
   - 提示系统与弹窗风格需要统一
   - 手机端/小屏体验需要再压一轮

3. 回合过渡机制不够流畅
   - 双方提交节奏不同时，展示阶段不同步
   - 结算后展示双方手势、再进入下一回合的过渡机制已开始做但需继续打磨

4. 联机异常提示不完整
   - 房间失效、对手退出、服务重启后的提示不够统一
   - 等待对方提交时的状态提示不够明显

【优先级：中】

5. 测试覆盖仍需继续扩展
   - 已覆盖规则引擎、房间管理、匹配逻辑、API 路由、存储恢复、Socket.IO 基础联动
   - 后续还需要补更多前端交互、异常路径、断线重连和多客户端端到端场景

6. 匹配系统还是单等待槽
   - 只支持一人等另一人的简单模式
   - 扩展性不足，不能做排队列表和超时重试优化

7. 前端脚本需要继续拆分
   - room_detail_page.js 仍偏大
   - 旧的 fetch / localStorage / 手写 modal 写法需要清理
   - 需要统一通过 ApiUtils / MessageUtils / ModalUtils 等入口

8. 路由命名仍有历史兼容入口
   - 本地模式已提供 /api/local/state、/api/local/step、/api/local/reset
   - 旧入口 /state、/step、/reset 仍保留用于兼容，后续可考虑标注废弃或逐步迁移

【优先级：低】

9. 安全性基本是原型级
   - 主要靠前端 localStorage token + 服务端校验
   - 后续公开后有冒充 token、刷接口、重复 join 等风险

10. 存在疑似未使用或历史遗留代码
    - 需要清理旧的函数和文件残留

四、建议的开发方向与优先级排序
================================================================================

第一优先级 ── 联机体验继续打磨
════════════════════════════════════════════════════════════════════════════════
  目标：让别人第一次打开网站就觉得——这不是一堆能跑的页面，而是一个真的联机游戏界面。

  □ 房间页、匹配页、主页的提示语统一
  □ 房间失效、对手掉线、服务重启后的提示更完整
  □ 匹配成功弹窗、退出房间弹窗、终局弹窗风格统一
  □ 手机端、小屏幕布局再压一轮
  □ 当前对局状态区继续优化
  □ 历史记录表格继续优化可读性
  □ 回合结束时双方手势展示阶段继续打磨
  □ 等待对方提交时的状态提示更明显
  □ 对方已选择 / 对方选择中 / 我方待选择 / 我方已选择状态层级统一

第二优先级 ── 前端结构与状态流整理
════════════════════════════════════════════════════════════════════════════════
  目标：不是重写，而是逐步把页面逻辑收成更清晰的层次。

  □ 继续把重复逻辑抽到共用模块
  □ 统一通过 ApiUtils 发请求
  □ 统一通过 MessageUtils 设提示
  □ 统一通过 ModalUtils 弹窗
  □ 统一通过 BootUtils 处理服务重启
  □ 统一通过 ResumeRoomUtils 处理房间恢复
  □ 清理旧的 fetch/localStorage/手写 modal 残留
  □ 把 room_detail_page.js 继续拆小
  □ 把 match_page.js 和主页脚本彻底收干净
  □ 减少模板里内联脚本和大块重复样式

第三优先级 ── 联机稳定性与测试补强
════════════════════════════════════════════════════════════════════════════════
  目标：让项目不只是现在看起来没问题，以后改动后也不容易出回归 bug。

  □ 补充联机外围测试：
    - 两人加入同一房间
    - 双方分别提交动作并结算
    - 非法 token 被拒绝
    - 观战身份不能提交动作
    - reset 双确认流程
    - 退出房间后匹配状态清理
    - 匹配成功后双方进入同一房间
    - 服务重启后缓存恢复/清理
    - 房间失效时前端正确处理
    - 对手退出时另一边正确收到事件
  □ 服务端日志统一（房间/匹配/过期清理日志）
  □ 错误码规范化

第四优先级 ── 新功能扩展
════════════════════════════════════════════════════════════════════════════════
  目标：先补最顺着现有结构长出来的功能，不要跳到很重的新系统。

  □ AI 模式正式接入——最小可玩版本（启发式 bot）
  □ 战绩/历史——最近对局记录、胜负统计、玩家统计
  □ 观战模式——无 seat 进入只能看不能操作
  □ 邀请体验优化——复制房间号、复制邀请链接
  □ 房主机制——房主专属操作、结束房间、重新开始

第五优先级 ── 长期产品化与部署完善
════════════════════════════════════════════════════════════════════════════════
  目标：让项目从自己能部署能玩变成给别人用也比较稳。

  □ 继续完善 Railway 部署配置
  □ 持久化策略更稳定（.db 文件不进仓库）
  □ 环境变量和配置整理
  □ 异常页更友好
  □ 服务重启后的恢复提示更完整
  □ 线上缓存与前端 boot 检测继续优化
  □ README / 部署说明补齐
  □ 后续扩展考虑：Redis、标准 session/token、更稳的 websocket

五、开发原则
================================================================================

1. 规则正确性 > 界面效果 > 代码优雅
2. 游戏状态以后端为准，前端只负责展示和提交
3. 规则引擎（app/game.py）优先保持稳定
4. 默认以最小修改、保持现有结构为原则，不轻易推倒重来
5. 如果能不动后端就先不动后端
6. UI 继续往 local 风格统一
7. 出现 bug 时，先定位是哪一层，再精确改那一层
8. 所有 Python 导入使用绝对路径（from app.xxx、from server.xxx）

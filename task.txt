二、剩余待办
================================================================================

【高优先级】

1. 浏览器端 E2E 实际执行
   - 脚本已写好（tests/e2e/），但环境缺少 playwright + requests
   - 需在本地安装后实际跑一次：
     pip install playwright requests
     playwright install chromium
     python -m pytest tests/e2e/ -v
   - 目标：确认多人房间在真实浏览器中无报错

2. 内部灰度上线
   - docs/step10_go_live.md 中的第一批（内部验证）还未实际执行
   - 需至少你和 1-2 人在真实环境完成 2.0 房间对战 + 回放验收
   - 启动前先跑：python scripts/migrate_battles.py --apply

3. 前端模板拆分
   - room_detail.html + room_detail_page.js 仍然偏大
   - v2/room.html + v2_room_page.js 同样需要拆分
   - 目标：按职责拆成大厅/玩家列表/操作区/结算展示/聊天区

【中优先级】

4. 联机异常提示统一
   - 房间失效、对手退出、服务重启后的提示仍不够统一
   - 断线/重连状态的用户可见性需加强

5. 安全性加固
   - 当前靠 session token + player_token 校验，属原型级
   - 需要：请求频率限制（Flask-Limiter）、防刷、防暴力注册

6. 压测与限流
   - 尚未做过正式压测
   - 需要：locust 或 wrk 脚本，验证 50+ 并发玩家
   - Socket.IO 消息频率限制

7. 聊天持久化
   - 当前聊天仅存房间内存 + 对局 JSON
   - 服务重启后未结束房间的聊天会丢失
   - 考虑独立聊天存储或定期刷盘

【低优先级 / 产品化】

8. 手机端多人布局打磨
   - 当前 2.0 回放页和房间页有基础响应式，但多人操作在手机上仍拥挤
   - 需要：玩家卡片折叠、动作选择适配小屏、目标选择触控优化

9. 房主高级设置
   - 自定义初始资源（HP/气/盾等）
   - 自定义速度层顺序
   - 房间密码、观战权限细化

10. 更完整的异常提示
    - 每种引擎拒绝原因对应明确的前端错误提示
    - 超时、网络错误、服务端错误区分显示

11. AI 多人玩家
    - 2.0 规则下 AI 需要能做目标选择、冲突协商决策
    - 目前只有 1.0 AI 占位页

12. 淘汰者/被淘汰者关系统计
    - 当前战绩统计有冠军次数/平均名次/分人数表现
    - 还没有"谁淘汰了谁"的关系数据（需在 RoundLogV2 中补充字段）

13. 旧 1.0 房间恢复兼容性
    - 服务重启后 v2 房间从 SQLite 恢复，但有 catch-all 跳过不兼容房间
    - 需确认线上无旧数据丢失

================================================================================
三、开发原则（不变）

1. 规则正确性 > 界面效果 > 代码优雅
2. 游戏状态以后端为准，前端只负责展示和提交
3. 默认以最小修改、保持现有结构为原则
4. 1.0 保持稳定，2.0 独立演进
5. 所有 API（除登录/注册外）必须经过 session 认证
6. 出现 bug 时，先定位是哪一层，再精确改那一层

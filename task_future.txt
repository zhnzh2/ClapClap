二、项目技术架构总览
================================================================================

前端层（Jinja2 模板 + 原生 JS）
  - 9 个模板页面（登录页公开，其余业务页面受 session 保护）
  - SessionUtils 统一管理登录态
  - ApiUtils 自动携带 X-Session-Token 请求头
  - ModalUtils 统一弹窗（确认/信息/成功）
  - AccountModal / AdminUsersModal 独立弹窗组件

服务层（Flask + Flask-SocketIO）
  - HTTP 路由：页面 + RESTful API + 认证 + 管理员
  - WebSocket 事件：房间状态 + 聊天广播
  - require_auth 装饰器全局身份校验
  - 业务逻辑层隔离路由与核心引擎

核心引擎层（app/）
  - GameEngine：回合结算
  - RoomManager：房间生命周期 + 聊天消息
  - Matchmaking：匹配队列
  - Storage：SQLite 持久化
  - Users：用户 CRUD + 验证 + 清理（CSV + 文件系统）
  - BattleRecorder：对战 JSON 存档 + 命名冲突解决 + rub 回收

持久化层
  - SQLite（storage.py）：房间 + 匹配
  - CSV（users.csv）：用户索引
  - 文件系统（User_X/）：用户详情 + 对战索引
  - JSON（battles/）：对战记录

数据目录结构（生产环境挂载 Volume）：
  data/
  ├── clapclap.db              # SQLite
  ├── users/
  │   ├── users.csv            # UID,用户名,密码,创建时间,已验证,权限
  │   └── User_X/
  │       ├── username         # 用户名
  │       ├── password         # 密码哈希
  │       ├── intro            # 介绍信
  │       ├── session          # 当前登录 token
  │       ├── created_at       # 创建时间（ISO 8601）
  │       ├── verified         # "0" 或 "1"
  │       ├── role             # "admin" 或 "user"
  │       └── battles          # 参与的对局 ID 列表
  ├── battles/
  │   ├── 202606161954013847.json
  │   └── rub/                 # 全员注销的对局
  └── _backup_repo/            # GitHub 备份仓库缓存

三、当前已知问题和观察
================================================================================

【优先级：高】

1. 前端模板文件偏大
   - room_detail.html 将 HTML/CSS/JS 集中在单文件
   - room_detail_page.js 仍偏大（含聊天逻辑）
   - 导致：难维护、难定位 bug、改动容易互相影响

2. 回合过渡机制不够流畅
   - 双方提交节奏不同时，展示阶段不同步
   - 结算后展示双方手势、再进入下一回合的过渡机制需继续打磨

3. 联机异常提示不完整
   - 房间失效、对手退出、服务重启后的提示不够统一

【优先级：中】

4. 安全性仍是原型级
   - 主要靠 session token + player_token 校验
   - 后续有冒充 token、刷接口、暴力注册等风险

5. 测试覆盖仍需扩展
   - 已覆盖核心引擎、API、账号密码校验、战绩并发与分页
   - 仍缺少浏览器端交互自动化和大规模并发压测

6. 匹配系统仍是单等待槽
   - 只支持一人等另一人的简单模式

7. 聊天系统无持久化独立存储
   - 聊天消息仅存在房间内存 + 对局 JSON 中
   - 服务重启后未结束房间的聊天会丢失

【优先级：低】

8. 战绩统计仍较基础
   - 已支持 Web 端分页查询和逐回合回放
   - 尚缺聚合胜率、常用动作和按对手筛选

9. 数据迁移/升级无自动化
   - CSV 格式变更需手动兼容

================================================================================
四、开发原则
================================================================================

1. 规则正确性 > 界面效果 > 代码优雅
2. 游戏状态以后端为准，前端只负责展示和提交
3. 规则引擎（app/game.py）优先保持稳定
4. 默认以最小修改、保持现有结构为原则，不轻易推倒重来
5. 所有 Python 导入使用绝对路径（from app.xxx、from server.xxx）
6. 用户密码不得明文存储（当前：SHA-256 + UID 盐值）
7. 所有 API（除登录/注册外）必须经过 session 认证
8. 出现 bug 时，先定位是哪一层，再精确改那一层
